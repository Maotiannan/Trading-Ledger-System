# Admin-Approved Customer Email Notifications Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Do not dispatch subagents unless the user explicitly authorizes them. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add durable, ADMIN-approved English/French customer email notifications for received payments, first Shipment Date entry, and first Release Date entry through Resend without allowing automatic customer sending.

**Architecture:** Customer contacts, templates, business-event tasks, immutable sent snapshots, delivery attempts, and webhook events live in the existing MySQL database. Receipt and Invoice writes call one transaction-aware projection service; an ADMIN action freezes recipients and content, and a separately triggered worker sends through a provider-independent Resend adapter. The frontend reads backend projections only and never calculates notification eligibility or sends directly.

**Tech Stack:** Next.js 16, React 19, TypeScript, Prisma 6.19.3, MySQL, Zod 4, Resend Node SDK 6.25.0, Jest, isolated API tests, Playwright, Docker Compose.

## Global Constraints

- Automatic customer sending is out of scope: every outbound message requires an explicit ADMIN approval action.
- SALES may maintain visible customers' notification emails and language preferences, but cannot access Email Management or any preview/send/cancel/retry/correction endpoint.
- Supported customer languages are `ENGLISH` (default) and `FRENCH`; UI labels are `English` and `Francais`.
- Global recipient modes are `PRIMARY_CC` (default) and `SEPARATE`.
- Payment, Shipment, and Release tasks are captured even while outbound sending is disabled; the feature switch blocks approval and delivery, not event persistence.
- `TRANSFER-*` receipts generated by Balance Transfer never create payment notification tasks.
- Signed-receipt drafts in `SIGNING_PENDING` create a task only when signing is finalized.
- One Invoice event produces one task per customer; orders for the same customer are combined and another customer's data must never enter the snapshot.
- Templates are editable, but rendering uses a fixed email-safe branded HTML shell and escaped controlled variables; no arbitrary script, attachment, Receipt image, Invoice PDF, or release document is sent.
- Resend credentials stay in environment variables. They must not be stored in MySQL, returned to clients, written to logs, or committed.
- The existing full `trading_ledger` MySQL backup covers all new durable data. No new persistent file directory is introduced.
- Deployment starts with outbound email disabled and test-delivery mode enabled; production recipient delivery is enabled only after domain and template approval.
