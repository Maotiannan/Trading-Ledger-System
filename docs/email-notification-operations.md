# Customer Email Notification Operations

This runbook is for MULEDGER administrators and operators. Customer-facing payment, shipment, and release messages are created as review tasks. The system never sends one until an ADMIN explicitly approves it.

## Safe Initial State

Every new installation starts with:

- outbound delivery: disabled;
- test mode: enabled;
- no sender address;
- no test destination;
- no Resend credential in the database.

Keep this state through migration, deployment, template review, and domain verification. Enabling outbound delivery still does not auto-send business events; it only allows an ADMIN-approved task to enter the delivery queue. While test mode is enabled, every approved delivery is redirected to the one configured test destination and no customer address is used.

## Resend Account And Domain

1. Add a sending subdomain owned by the company in the Resend Domains dashboard. A dedicated subdomain such as `notice.example.com` isolates transactional-mail reputation from ordinary staff mail.
2. Copy the exact SPF/MX and DKIM records generated by Resend into the DNS provider. Do not reuse example values from this document.
3. Wait until Resend reports the domain as `verified`.
4. Add DMARC after SPF and DKIM pass. Start with monitoring policy `p=none`, inspect reports, then move to `quarantine` or `reject` only when all legitimate senders are known.
5. Choose a sender address on the verified domain and an optional reply-to mailbox that staff actively monitor.

Official references:

- [Resend domain verification](https://resend.com/docs/dashboard/domains/introduction)
- [Resend DMARC guidance](https://resend.com/docs/dashboard/domains/dmarc)

## Environment Secrets

Create a domain-scoped sending key where possible and a webhook endpoint in Resend. Store the resulting values only in the deployment environment:

```dotenv
RESEND_API_KEY=""
RESEND_WEBHOOK_SECRET=""
EMAIL_DELIVERY_BATCH_SIZE="25"
EMAIL_DELIVERY_LOOP_SECONDS="30"
```

Rules:

- never paste a real key into Git, System Settings, screenshots, tickets, logs, API responses, or this runbook;
- the browser receives only `apiKeyConfigured` and `webhookSecretConfigured` booleans;
- the delivery trigger receives the existing maintenance token, not the Resend credentials;
- use different Resend keys and webhook endpoints for production and isolated test environments.

The production webhook URL is:

```text
https://muledger.dainty.vip/api/webhooks/resend
```

Subscribe it to the events processed by MULEDGER:

- `email.sent`
- `email.delivered`
- `email.delivery_delayed`
- `email.bounced`
- `email.complained`
- `email.suppressed`
- `email.failed`

Resend signs each request. MULEDGER verifies the unmodified raw body with `svix-id`, `svix-timestamp`, `svix-signature`, and `RESEND_WEBHOOK_SECRET`; duplicate event IDs are stored only once and old events cannot move a completed delivery backward. If a valid event arrives before the sending worker has stored Resend's message ID, MULEDGER keeps the event and returns `503`; Resend then retries it, and the duplicate event is linked and applied after the message ID is available instead of being discarded.

Official references:

- [Resend webhook event types](https://resend.com/docs/webhooks/event-types)
- [Resend webhook retries and replays](https://resend.com/docs/webhooks/retries-and-replays)
- [Resend API key handling and rotation](https://resend.com/docs/knowledge-base/how-to-handle-api-keys)

## MULEDGER Settings

In `Settings -> Email Notification Settings`, ADMIN configures:

- sender name and verified sender address;
- reply-to address;
- company logo HTTPS URL;
- primary-plus-CC or separate-message handling for customers with multiple addresses;
- retry count and intervals;
- test destination;
- English and French payment, shipment, and release templates.

Customer notification addresses and language preference are maintained in Customer Management within the existing account visibility tree. They are optional. SALES may maintain visible customer contact data but cannot view Email Management, preview a task, approve sending, retry, cancel, or create a correction.

Before enabling outbound delivery:

1. Confirm both credential indicators are configured.
2. Confirm Resend shows the sending domain as verified.
3. Save the exact sender and monitored reply-to addresses.
4. Keep test mode enabled and set one internal test destination.
5. Preview all six templates on desktop and mobile.
6. Create isolated payment, first-shipment, and first-release events.
7. Approve only those test tasks and confirm the test mailbox receives them.
8. Confirm Email Management records the attempt and the webhook advances delivery state.
9. Disable test mode only after the content, recipients, domain authentication, and delivery history are verified.

## Daily Operation

- Business writes create or refresh durable tasks; they do not send email.
- ADMIN reviews current source values and recipients in Email Management.
- Approval freezes recipients and rendered content so later customer edits cannot rewrite what was approved.
- `email-delivery-trigger` calls the internal dispatch endpoint every configured interval and atomically claims queued deliveries.
- Provider acceptance, retry, uncertainty, bounce, complaint, suppression, and webhook events remain in MySQL for audit.
- If a Receipt or Invoice changes while an approved email is already being sent, the delivery history may still complete, but the task remains `Needs Correction`; delivery completion and later webhooks cannot hide that source change.
- A timeout with an unknown provider outcome becomes `Delivery Uncertain`; do not blindly retry it because that can duplicate customer mail. ADMIN must explicitly confirm the retry.
- A changed business source is not silently reused. Create a correction task from the original sent history when a follow-up is required.

Trigger health can be checked without sending a new customer message:

```bash
docker compose ps app email-delivery-trigger
docker compose logs --tail=100 email-delivery-trigger app
```

Do not print environment variables while collecting logs. Search the Email Management delivery history for the task rather than querying provider secrets.

## Quota And Cost

As checked against Resend's official pricing on 2026-09-02, the Free transactional plan includes 3,000 sent/received emails per month and 100 per day. Each To/CC/BCC recipient counts separately. Paid plans remove the daily cap and use plan-specific monthly quotas and overage pricing. Recheck [Resend pricing](https://resend.com/pricing) before enabling production because limits and prices can change.

Use the separate-recipient mode only when its privacy benefit justifies the higher message count. The system-level mode applies consistently to all customers.

## Key Rotation

Resend keys do not expire automatically. Rotate without interruption:

1. Create a new key with the same or narrower permissions and domain scope.
2. Replace `RESEND_API_KEY` in the deployment environment.
3. Recreate only the application service through the safe deployment flow.
4. Send one ADMIN-approved test-mode message and verify the request in Resend plus the attempt in MULEDGER.
5. Delete the old key only after the new key is proven active.

For webhook-secret rotation, create or rotate the Resend webhook, update `RESEND_WEBHOOK_SECRET`, deploy, and use Resend's test event before retiring the old endpoint. Plan a brief event-processing window because the application accepts one webhook secret at a time.

## Backup And Recovery

All customer addresses, language preferences, templates, tasks, frozen sent content, deliveries, attempts, and webhook events are in the complete `trading_ledger` database dump. No new NAS file family is created. Credentials are deliberately excluded from backups and must be restored from the operator's secret store.

Recovery and migration evidence is recorded in [the 2026-09-02 email migration drill](backup/restore-drills/2026-09-02-email-notifications-migration-drill.md). The general database and media procedure remains [the MULEDGER backup runbook](backup/muledger-local-backup.md).

## Rollback

1. Disable outbound delivery in Settings.
2. Stop only `email-delivery-trigger`.
3. Preserve all email tables and delivery history.
4. Roll back the application to the prior verified image.
5. Investigate and deploy a forward fix; do not delete records to hide a failed or incorrect send.

An application rollback does not require dropping the additive email schema. Data removal, if ever needed, is a separate migration requiring an explicit backup and approval.
