# Fixed-image site releases

This procedure is for a **previously adopted** fixed-image MuLedger site. If the running app uses a different worktree or a chain of overrides, the generic preflight must refuse. Read that active release's private `DEPLOYMENT.md`; do not bump the version, switch checkouts or run plain Compose to bypass the refusal.

- Keep the site environment at its protected existing source. The adopted main checkout has an ignored `out/site-releases/site.env` link to that source and immutable `out/site-releases/<version>/site.override.json` files. Each overrides only the fixed local app image, OCI version label, `node server.js` command, and existing private Caddy configuration mount. Do not commit site files or expanded Compose output.
- Before first adoption, run `node scripts/check-site-compose.mjs ENV_FILE SITE_OVERRIDE` read-only. It renders the live chain and candidate, checks the running app and prints only hashes and configuration metadata. Unchanged image at adoption: the **only** permitted diff is the build context. Use the deployment record and approved window for the initial cutover; never join it to a migration or credential change.
- For later releases, build and test a clean, reviewed revision into a local immutable image. Check the version **inside** that image in isolation. Keep the previous image and override. From main run `bash scripts/rebuild-local-app.sh --check-only`, then `node scripts/check-site-compose.mjs out/site-releases/site.env "$CANDIDATE"`. Review the version, digest and changed fields. Configuration drift, including environment and storage changes, needs its own reviewed deployment.
- Only with authorization for that version/window, run `bash scripts/rebuild-local-app.sh --release "$CANDIDATE"` with the **absolute** registered override path. Only app is recreated, with no dependencies, build, pull or migrations. Confirm service IDs for Caddy, maintenance, and all three triggers are unchanged. Check the local and public homepage and unauthorized API response. Never test release health by dispatching messages or running maintenance.
- For rollback to a previous registered version use `bash scripts/rebuild-local-app.sh --rollback "$PREVIOUS"`. If app cannot start or the checker refuses, stop and use the authorized fallback from the last private deployment record (preserved configuration, image and environment); do not improvise. Record stage, exit code, sanitized stderr/logs and data risk. Neither code rollback nor a failed health check calls for restoring customer data.

### A bounded native build

Do not cold-build on a shared application host without a measured budget. The **ARM64 image profile** Actions workflow uses a separate native Linux ARM64 runner on a public repository. On a short branch it compares with its main ancestor; manual runs accept the prior application commit/tag. The workflow uses only tracked sources and synthetic fixtures. It does not push a registry image or deploy.

BuildKit verifies the actual compiler cgroup (memory, zero swap, two CPUs and one build step at a time). A candidate is exercised both with the generic migration entry point on empty MariaDB and as the site's `node server.js` on isolated MySQL. The latter uses the existing schema test adapter, not a migration. Compare cold build memory (including anonymous memory, separate from page cache), image sizes, and application latency/RSS independently. The one-day artifact contains the **tested** Docker image, image ID/revision, and transport checksum. Verify all three and the packaged version before considering it for a fixed-image release. An artifact is not permission to switch the site.
